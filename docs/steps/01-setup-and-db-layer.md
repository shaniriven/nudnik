# Step 1 — Project setup & installments (Postgres + Prisma schema + DB repositories)

Build-order step 1 of `docs/architecture.md` section 9. This is a self-contained
implementation brief: an implementing agent should be able to execute it without
any other context beyond this repo (`CLAUDE.md`, `docs/architecture.md`,
`docs/sheets-design.md`).

## Context

Nudnik is currently docs-only (`CLAUDE.md`, `docs/architecture.md`,
`docs/sheets-design.md`, `.env.example`, `.gitignore` — no `package.json`, no
`src/`). Per `docs/architecture.md` section 9, the build proceeds **one step at
a time, with tests, before moving on** (also stated in `CLAUDE.md` working
rules). This document covers **only step 1**:

> "Railway Postgres provisioned, Prisma schema + first migration, DB
> repositories — the foundation now includes `bot_users` alongside the two
> original tables"

Nothing from later steps (Sheets, Gmail, Claude extraction, Telegram) should be
scaffolded yet — just the project skeleton, the DB layer, and its tests, per
section 8's standards (TS strict, zod at boundaries, structured logging
conventions established, tests shipped with the module).

Decisions already made for this step:
- **Local/test Postgres runs in Docker** (docker-compose) — Railway Postgres is
  provisioned separately for deploy, not used for local dev/test.
- **Vitest** as the test runner.
- **npm** as the package manager.
- Railway project/Postgres **not yet provisioned** — manual CLI steps are
  listed below, decoupled from local work so they aren't a blocker.

## Scope of Step 1

1. Project scaffold: `package.json`, strict `tsconfig.json`, ESLint + Prettier
   + husky/lint-staged, Vitest config.
2. `docker-compose.yml` with two Postgres services (dev DB + disposable test
   DB).
3. `src/config/env.ts` — zod-validated env loader (section 8e), covering every
   var in `.env.example` plus a new `TEST_DATABASE_URL`.
4. `prisma/schema.prisma` — the three models from architecture.md section 5
   (`ProcessedEmail`, `PendingTransaction`, `BotUser`), first migration via
   `prisma migrate dev`.
5. `src/db/prismaClient.ts` — singleton client.
6. `src/db/repositories/` — `processedEmailRepo.ts`, `pendingTransactionRepo.ts`,
   `botUserRepo.ts`, with only the CRUD primitives step 1 itself needs (not the
   full query surface later steps will add, e.g. the `/pending` digest query
   comes in step 9).
7. Integration tests per repo, each wrapped in a transaction that's rolled back
   after (section 8d) — run against the Dockerized test DB.
8. Manual Railway provisioning steps (CLI), for a human to run outside of local
   dev.

## Key implementation details

**docker-compose.yml** — two services, e.g. `postgres-dev` (port 5432) and
`postgres-test` (port 5433), both throwaway local containers, volumes only for
the dev one (test DB stays ephemeral).

**Prisma schema** — copy the three models from architecture.md section 5
verbatim (`ProcessedEmail`, `PendingTransaction` with its relation to
`ProcessedEmail`, `BotUser`), including the `@@map`/`@map` snake_case mappings
already specified there. Run `npx prisma migrate dev --name init` against
`postgres-dev`.

**Repositories accept an injectable client** — each repo function takes the
Prisma client (or a `Prisma.TransactionClient`) as its first parameter instead
of importing the singleton directly, e.g.:
```ts
export function createBotUser(db: PrismaClientOrTx, data: {...}) { ... }
```
This is what makes the "wrap each test in a transaction, roll it back after"
requirement from section 8d actually achievable: tests call
`prisma.$transaction(async (tx) => { ...call repo fns with tx...; throw new
RollbackSignal(); })` and catch the sentinel error, so no test writes persist.
The app's real call sites (later steps) just pass the singleton client, so
this costs nothing in production code paths.

**Repo functions for step 1** (minimal, only what's needed now — later steps
add more as those features are built):
- `botUserRepo`: `findByChatId`, `create`, `deleteByChatId`
- `processedEmailRepo`: `findByGmailMessageId`, `create`, `updateStatus`
- `pendingTransactionRepo`: `create`, `findById`, `updateStatus`

**env.ts** — zod object validating every `.env.example` key (including the new
`TEST_DATABASE_URL`) at startup; throws with a clear aggregated message
listing every missing/invalid key, not just the first one.

## Manual steps (human-run, outside automation)

1. `railway login`, `railway init` (or link existing project) for the Nudnik
   project.
2. `railway add` → provision the Postgres plugin.
3. Capture the generated `DATABASE_URL` from Railway's dashboard/CLI — store
   it for later deploy steps (section 7 of the build order splits into two
   services; that's when this is actually wired up). Not needed for local
   dev, which uses the Dockerized DB instead.
4. Docker Desktop (or equivalent) must be running locally before
   `docker compose up -d`.

## Verification

1. `docker compose up -d` → both Postgres containers healthy.
2. `npx prisma migrate dev --name init` runs clean against the dev DB;
   `npx prisma studio` shows the three empty tables with correct columns.
3. `npm run lint` and `npm run build` pass with zero errors (strict TS, no
   `any`/`@ts-ignore` without justification).
4. `npm test` — all repository integration tests pass against
   `postgres-test`, and re-running the suite twice in a row produces
   identical results (proves rollback is actually working, not leaking rows).
5. `npm run test -- env.test.ts` — confirms `env.ts` fails fast with a clear
   message when a required var is missing, and passes when `.env` is fully
   populated.
